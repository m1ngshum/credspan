# CI verification and caches

Every PR runs the dependency-free foundation, classifier, required-gate and peer-cache orchestration checks. Only changes limited to the explicit root document list in `scripts/ci-plan.mjs` and Markdown under `docs/` qualify for this fast lane. The classifier reads the aggregate PR merge-base diff with renames disabled, so both old and new paths are checked. Empty, unavailable or malformed diff evidence selects full verification. Unknown paths, assets, runtime, tests, dependencies, lockfiles, workflows, build scripts and operations changes select full verification. Main pushes always select full verification.

The required `ci` job always runs. It accepts the documentation lane only when the fast checks succeed and every runtime lane is skipped as expected. Full verification requires native AMD64 and ARM64, integration, browser, operations and MCP jobs to succeed. Failed, cancelled, unexpectedly skipped or missing results fail the gate. Workflow-level path filters are deliberately absent. New PR revisions cancel superseded runs for that PR and workflow; main pushes and the separate manual private artifact workflow retain their verification.

The wallet peer cache contains the tested complete wallet runtime jars, upstream notices, ordered classpath and qualification manifest, separately keyed for each OS and architecture. Its key includes the exact upstream source revision (including the Gradle wrapper and dependency declarations), preauthorized and dependency patch digests, JDK and base-image digests, requested Gradle test/build arguments and both peer build scripts. Changing any of those inputs invalidates the cache. `build-peer.mjs` validates the manifest, exact flat regular-file inventory and every file’s SHA256 before using it; absent or corrupt entries rebuild and run the upstream JVM tests. The digest-pinned Docker image is assembled on both cold and warm paths, and the existing real wallet/MCP checks still run on every relevant change.

CI requests the full qualified key without `restore-keys` fallbacks. GitHub can still [prefix-match the primary key](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-key-matching); the builder independently requires an exact manifest key and inputs before using the distribution. Only successful main push jobs save caches, after their real compatibility checks pass; PR and fork jobs never save executable caches for privileged or default-branch consumers. GitHub's cache ref isolation is part of this trust boundary. Manifest/digest validation detects corruption and mismatched inputs, not a hostile writer replacing both runtime files and manifest. No secrets, source checkout, raw build logs, credentials or Docker socket enter the cache. Local callers can opt in with `CREDSPAN_PEER_CACHE=/absolute/cache/path node vendor/waltid/build-peer.mjs`; that directory must be trusted.

The first run for a new key is cold; PRs cannot seed the main cache and remain cold until a successful main run seeds each architecture. Cache eviction also causes a rebuild. No Gradle or Docker export/import cache is added. The complete runtime cache is larger than the former single-jar cache; measure actual hosted behavior before claiming savings. pnpm installation remains frozen and unchanged pending evidence that additional dependency-cache plumbing pays for itself. Hosted cold/warm measurements are still required before claiming runner-minute or monetary savings; local orchestration tests do not qualify an actual wallet artifact or replace hosted CI.
