# Local membership verification and revocation

The authenticated presentation API accepts the local managed membership cohort only. It is a fixed, synthetic sandbox profile: final OpenID4VP 1.0 DCQL, encrypted `direct_post.jwt`, `dc+sd-jwt`, EdDSA issuer signatures, P-256/ES256 holder binding, and required signed nonselective `vct`, `jti`, `exp` and `status` claims. The default query requests `memberId` only; it does not request the member's name. Unknown issuers, absent or selectively disclosed status, other status destinations, invalid proofs, expired credentials and revoked credentials fail closed. This is not national identity conformance or production authorization.

All `/api` operations use the configured administrator `Authorization: Bearer …` management key. The local console accepts this key only in memory; never embed it in browser bundles, storage, URLs or logs. These endpoints do not provide tenant isolation.

| Operation | Request | Result |
| --- | --- | --- |
| `POST /api/presentation-requests` | `{}` only | `id`, wallet `request` URL, original `expiresAt` |
| `GET /api/presentation-requests/:id/result` | Stored session UUID | Minimal historical/current result |
| `POST /api/credentials/:id/revoke` | Stable `urn:uuid:…` credential ID from issuance, `{}` body | Idempotent `{credentialId, revoked:true}`; unknown ID is 404 |
| `GET /status-lists/:cohort` | Public, no bearer key | Signed `application/statuslist+jwt`, `Cache-Control: no-store` |

A successful result contains `accepted`, immutable `verifiedAt`, `checkedAt`, original `authorizationExpiresAt`, and the credential ID, member ID and credential expiry. No raw credential, presentation, grant, holder key or name is returned. Sessions without a completed verification record return `accepted:false` without a verification timestamp. A persisted proof outcome can survive an ambiguous or failed final HTTP response; its timestamp alone never establishes current acceptance. After a previously successful presentation becomes invalid, the result retains its historical `verifiedAt` and original deadline but returns `accepted:false` without credential attributes. Unavailable session/receipt storage returns 503; a failed current credential/status check returns `accepted:false`.

`verifiedAt` records the original proof outcome. `checkedAt` records the completed current check. Each result read re-verifies the stored SD-JWT and holder signature with the original audience and nonce, current trust, expiry and signed status. It never creates a new authentication event, changes `verifiedAt`, or extends the original presentation authorization lifetime. Callers must treat that original deadline as an upper bound, not turn polling into renewed authorization. The API checks both credential and authorization deadlines again after awaited verification, receipt persistence and final session persistence; a failed or ambiguous attempt requires a fresh request. Compatibility `/api/roundtrips/:id` still reports only raw cryptographic state and is not an acceptance API.

## Trust and status boundary

Omitting `TRUSTED_ISSUER_DIDS` trusts this store's explicitly persisted local issuer DID. Set a JSON array of `did:key` identifiers to replace that allowlist; `[]` denies all credentials. Configuration is loaded at startup, so apply a consistent policy to every worker and restart them for changes. This first implementation additionally requires the managed local issuer, exact local status URI and durable credential allocation. Adding another DID to the allowlist does not enable arbitrary external issuers/status providers. No remote DID resolver or generic outbound status fetch is enabled.

The status URI is resolved internally to a newly signed local snapshot through Credo's installed `agentDependencies.fetch` API. Other URIs are rejected without network access, so redirects cannot be followed. Generation is bounded to two seconds and the returned token to 16 KiB. Status JWTs must use `statuslist+jwt`, EdDSA, the exact local absolute/relative signing key reference and issuer, the exact subject URI, one-bit entries, integer issuance/expiry, and a 30-second TTL/lifetime with no future issuance or stale tokens. Credo still verifies the status JWT signature and status bit; parsing or a direct database revocation lookup is not a substitute. An additional durable revocation check denies credentials even if a concurrent snapshot predates revocation. Internal verification does not cache status. Timeout does not cancel native storage work already in progress.

The wire format follows the implemented JWT Token Status List profile using installed Credo 0.7.4, `@owf/token-status-list` 0.4.2 and `@sd-jwt/sd-jwt-vc` 0.21.1. [TSL draft-21](https://datatracker.ietf.org/doc/draft-ietf-oauth-status-list/) remains an Internet-Draft in the RFC Editor queue as checked on 2026-11-12; [SD-JWT VC draft-26](https://datatracker.ietf.org/doc/draft-ietf-oauth-sd-jwt-vc/) is also an Internet-Draft. The tested library behavior does not establish complete latest-draft conformance.

## Durable concurrency and limits

Each offer reserves one of 1024 one-bit status indices using a native unique Askar insert, starting at a random index and probing on genuine duplicate errors only. An immutable mapping binds the stable credential ID, issuance session and index. Allocation occurs before the offer is returned and is required before signing. Indices are never recycled, including failed offers; list exhaustion fails issuance. Use a fresh disposable store when exhausted. This small fixed list, cohort correlation and unresolved retention are sandbox limitations.

Revocation inserts one immutable record per index. Duplicate revocation succeeds, other storage errors fail closed. Each signed list is generated from the complete durable revocation snapshot; competing workers never overwrite a shared mutable bitset. This protects concurrent revocations without claiming a global transaction between verification, revocation and API response. An operation concurrent with revocation can linearize before it; subsequent reads recheck current state.

The original one-attempt native verification claim still excludes concurrent/replayed responses across processes. Verification receipts are unique immutable records. A crash between receipt persistence and Credo's session update may leave an unusable receipt; only `ResponseVerified` sessions with a valid current proof/status and unexpired authorization can return accepted. Claims, receipts and revocations must not be erased to retry. Database restore can rewind them and lose revocations: recovery must fence old workers, invalidate old sessions and recover revocations or deny the affected cohort before reopening traffic. The [bounded local operations drill](operations.md) now exercises external fencing, credential invalidation and complete managed-cohort retirement before reopening, with downtime and reissue.

## Validation

`pnpm check`, `pnpm test:integration` and `pnpm test:storage` exercise real native crypto/PostgreSQL. Integration uses the pinned, explicitly modified walt.id Wallet API v2 peer, not Credo as its own holder. Tests cover valid issuance/hold/selective presentation; actual HTTP replay, disclosure tampering and binding rejection; missing/unapproved/selective status; a foreign-key status token that spoofs the expected issuer; stale/unavailable/invalid-signature status; explicit empty trust; deadlines crossed during an awaited verification; independent-process index allocations/revocations; signed snapshots retaining every revocation; restart persistence; and unavailable database denial. The peer build provenance and platform limits remain in [compatibility evidence](compatibility.md). Hosted CI is still required before merge.
