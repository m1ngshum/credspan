# Compatibility evidence and boundaries

The implemented lane is a fixed membership profile with authenticated bounded synthetic issuance inputs, not a general issuer/verifier platform. Stack: Node 26.13.1, NestJS (`@nestjs/common` 12.6.0, `@nestjs/core` 12.5.0, `@nestjs/platform-express` 12.5.0, `@nestjs/swagger` 12.1.2), Express 5.3.0, Credo 0.7.5, native OWF Askar 0.6.1 and PostgreSQL 18.6. The Askar package uses its upstream bundled/downloaded native library; package version alone is not the native-library version. Native signing/verification and tampered-message rejection were exercised on macOS arm64, Linux arm64 and emulated Linux amd64; emulation is not physical amd64 qualification. Those are the original local results; the reviewed PR2–5 hosted native AMD64/ARM64 checks subsequently passed. New runtime/MCP changes require their own exact-head CI results; API checks do not imply native AMD64 MCP qualification.

A real independently implemented holder is the [modified walt.id Wallet API v2 1.2.1 peer](../vendor/waltid/README.md). Stable unmodified walt rejects valid preauthorized-only metadata lacking `response_types_supported`. Our reviewed narrow peer patch honors OID4VCI final §12.2 and preserves strict errors for malformed/inconsistent grant metadata. It was built from the pinned public source with 591 real JVM tests passing, including model/serialization cases. The API never advertises unconfigured authorization-code capabilities merely to silence that parser. Rebuild provenance is printed by the peer build script; no peer image is published.

The lane uses final OID4VCI 1.0 preauthorized code, `dc+sd-jwt`, real ES256 holder binding, and final OID4VP 1.0 DCQL encrypted `direct_post.jwt`. It does not use Credo as its own holder. The runtime's shared verification-service boundary makes a durable unique native Askar insert for an already-resolved stored session before delegating cryptography. This protects every Credo dispatch path at that boundary, not just a process-local mutex. The [issuer API](issuance.md) now applies separate atomic claims to validated token redemption and one-credential issuance; unsupported requests are rejected before those claims. See the runbook for the deliberate one-attempt/failed-response policy.

## Dependency risks

No Drizzle adapter is installed: Credo's adapter requires `drizzle-orm ^0.44.6`, which excludes the fix for [GHSA-gpj5-g38j-94v9](https://github.com/advisories/GHSA-gpj5-g38j-94v9) in 0.45.2. Native Askar provides PostgreSQL storage directly.

Credo core still installs old `@sd-jwt/decode` via PEX/Sphereon, affected by [GHSA-f9j6-8p6x-r9j6](https://github.com/advisories/GHSA-f9j6-8p6x-r9j6). The actual locked graph audit on 2026-11-12 reports one high advisory (this decoder), zero moderate/critical; it is not a clean audit. Do not suppress the audit or override split legacy packages with merged APIs. Native Credo SD-JWT verification uses current `@sd-jwt/core`; the bounded final/DCQL route excludes PEX. Tests cover correct holder re-signing/recomputed `sd_hash` when rejecting tampered/unreferenced disclosures, duplicates and malformed disclosures, with valid selective omission controls. HTTP tests add PEX sentinels and reject forged credentials with remote issuer/holder DIDs without invoking a network DID resolver. The configured DID resolver set contains only local did:key methods; holders use inline JWKs. These route-specific checks do not eliminate the installed advisory or qualify future holder/PEX routes; reassess the dependency graph before expanding scope.

## Future ecosystems

This lane is not conformance with any national identity ecosystem. [Switzerland's swiyu](https://swiyu-admin-ch.github.io/specifications/) adds DID:webvh, status and ecosystem trust requirements; [UK wallet verification](https://docs.wallet.service.gov.uk/verify-credentials/) describes mdoc/W3C VCDM2 profiles; [NIST wallet guidance](https://pages.nist.gov/800-63-4-Implementation-Resources/scw/index.html) discusses secure presentation profiles; [EUDI issuers](https://docs.eudi.dev/latest/build/build-your-issuer/) cover mdoc and SD-JWT. These need separately selected profiles, trust anchors, status/revocation, conformance and recovery evidence. The compatibility demo does not establish any of them.

Production authentication/authorization, tenant isolation, resource quotas, broader ecosystem trust policy, operational retention, production backup/key recovery and production network isolation remain future roadmap work. The [local operations drill](operations.md) now qualifies disruptive managed-cohort recovery and store rekey within the bounded sandbox. `ResponseVerified` is cryptographic evidence only; it is not business authorization or production acceptance.

Each runtime initializes one agent. Persistence tests cover PostgreSQL restart, a separate application process, and graceful application teardown/recreation with a new agent in the same process; signing identity, records and immutable claims persist. In-place reconnection of an existing agent during an outage and automatic failover have not been qualified. Restoring a database can rewind consumption claims; the local operations recovery deliberately retires the entire managed cohort before reopening traffic.

The [verification API](verification.md) now applies an explicit local issuer/profile policy and real signed Token Status List checks, with authenticated idempotent revocation. Current result reads preserve historical verification time while rechecking proof, expiry, trust and revocation within the original request lifetime. This qualifies only the managed local cohort, not arbitrary external issuers or national profiles.

PR5's initial generator install added three high `js-yaml` 4.2.0 advisories through latest Hey API 0.99.0 / parser 1.4.4. A specifically qualified child-only 4.3.2 security patch now removes those three findings; the fresh full-graph audit again reports **one high, zero moderate/critical**, the existing decoder. See [dependency patch provenance](dependency-patches.md) for upstream tests, exact scope, unchanged generated output and retirement criteria. Local JSON/internal-reference checks remain an additional input boundary, not a substitute for the patch.

The 2026-11-13 follow-up adds exact-version security backports for both legacy decoder entrypoints, with actual Sphereon/PEX caller compatibility and adversarial traversal tests; see [patch provenance](dependency-patches.md). The raw audit still reports the original version advisory. Route restrictions remain in place; this does not enable PEX or claim a clean graph.
